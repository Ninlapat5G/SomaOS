# SomaOS

**แนวคิดหลัก:** ทุกวันนี้ AI agent (โปรแกรมที่ใช้ LLM อย่าง ChatGPT/Claude เป็นสมอง) มักจะ "ยัด" ทุกอย่างที่เคยเจอ — ประวัติการคุย ข้อมูลตัวละคร เหตุการณ์ต่าง ๆ — เข้าไปใน prompt ทุกครั้งที่ต้องคิดอะไรสักอย่าง วิธีนี้ทำให้ค่าใช้จ่าย (token) พุ่งสูงขึ้นเรื่อย ๆ ตามขนาดของประวัติ และยิ่งยัดเยอะ คุณภาพก็ไม่ได้ดีขึ้นตามสัดส่วนที่จ่ายไป

**SomaOS** คือความพยายามแก้ปัญหานี้ด้วยแนวคิดแบบ "ระบบปฏิบัติการจัดการหน่วยความจำ" — แทนที่จะให้ตัว LLM เป็นคนตัดสินใจเองว่าจะจำอะไร/ลืมอะไร (ซึ่งแพงและคาดเดาผลไม่ได้) เราให้ **โปรแกรมภายนอกที่มีกฎตายตัว (deterministic policy)** เป็นคนตัดสินใจแทนว่า ณ ขณะนี้ควรเอาความจำชิ้นไหนใส่เข้าไปใน context ของ LLM บ้าง คล้ายกับที่ระบบปฏิบัติการคอมพิวเตอร์ตัดสินใจว่าจะเก็บข้อมูลอะไรไว้ใน RAM (เร็วแต่จำกัด) กับอะไรที่พักไว้ใน disk (ช้าแต่จุเยอะ)

หลักการสั้น ๆ: **"Engine เป็นคนถือโลก โมเดล (LLM) เป็นคนถือความฉลาด"** — ตัวโปรแกรมเก็บสถานะทั้งหมดของโลกจำลอง ส่วน LLM จะถูกเรียกใช้เฉพาะตอนที่ต้อง "คิด" หรือ "ตัดสินใจ" อะไรที่ซับซ้อนจริง ๆ เท่านั้น

รายละเอียดเชิงลึก (สถาปัตยกรรม เหตุผล งานวิจัยที่เกี่ยวข้อง) อยู่ใน [`target_SomaOS.md`](target_SomaOS.md) — เอกสารหลักของโปรเจกต์นี้

## สถานะตอนนี้: Phase 0 ปิดรอบทดลองแล้ว — ผลคือ **ยังไม่ผ่านเกณฑ์**

โปรเจกต์นี้**ยังไม่ใช่ระบบที่ใช้งานจริงได้** — Phase 0 เป็นขั้น "วิจัยทดลอง" (research spike) ที่ตอบคำถามเดียวก่อนว่า **แนวคิดนี้มันเวิร์กจริงไหม** ก่อนจะลงทุนสร้างระบบเต็มรูปแบบ ตอนนี้ทดลองจบรอบแล้ว วัดผลเต็มสเกล (ไม่ใช่แค่ทดลองย่อย) แล้วสรุปตามกฎที่ตั้งไว้ตั้งแต่ต้น

สิ่งที่สร้างไว้ใน Phase 0 มีแค่ 3 อย่าง:

1. **เครื่องคิดคะแนนความสำคัญของความจำ** (retention scoring) — ให้คะแนนแต่ละ "ชิ้นความจำ" ว่าควรเก็บไว้ใกล้ตัวแค่ไหน โดยดูจาก ความใหม่, ความถี่ในการใช้, ความเกี่ยวข้องกับเป้าหมายปัจจุบัน, และ "ความน่าประหลาดใจ" (สิ่งที่ขัดกับความเชื่อเดิม)
2. **ตัวจัดสรรพื้นที่ความจำ** (working set allocator) — ตัดสินใจว่าด้วยงบ token ที่มีจำกัด จะเก็บความจำชิ้นไหนไว้ "ใกล้มือ" บ้าง
3. **ตัวเทียบกับคำตอบที่ดีที่สุดในทางทฤษฎี** (OPT oracle) — จำลองว่า "ถ้ารู้อนาคตล่วงหน้า ควรเก็บอะไรไว้บ้าง" เพื่อใช้เป็นเกณฑ์เทียบว่าเราทำได้ดีแค่ไหนเมื่อเทียบกับคำตอบที่ดีที่สุดที่เป็นไปได้

ทุกอย่างในขั้นนี้ **ไม่มีการเรียกใช้ LLM เลย** — ทดสอบด้วยข้อมูลจำลอง (synthetic) ที่สร้างขึ้นเองแบบมีคำตอบที่ถูกต้องชัดเจน (ground truth) เพื่อให้วัดผลได้แม่นยำและรันซ้ำได้ผลเดิมทุกครั้ง

### ผลการทดลองสุดท้าย (เต็มสเกล — ไม่ใช่แค่ทดลองย่อยอีกต่อไป)

รันการทดลองเต็มรูปแบบ (8 สถานการณ์จำลอง × 4 ระดับ budget × 3 ค่าพารามิเตอร์ × 11 เมล็ดสุ่ม × 6 policy = 6,336 การทดลองย่อย) เปรียบเทียบ policy ของเรา (เรียกว่า `S`) กับ baseline อื่น ๆ

**ผลคือไม่ผ่านเกณฑ์ที่ตั้งไว้ทั้ง 4 ข้อ** (ดูรายละเอียดเกณฑ์ใน `target_SomaOS.md` หัวข้อ 7.4) และไม่ใช่แบบก้ำกึ่ง — ทุกข้อห่างจากเกณฑ์พอสมควร เช่น `S` ยังแพ้ baseline ง่าย ๆ ที่ค้นหาด้วยความคล้ายของหัวข้อ (naive RAG) อยู่ชัดเจนเมื่อเฉลี่ยรวมทุกเงื่อนไข

**แต่ที่น่าสนใจคือ `S` ไม่ได้แพ้ตลอด** — ในสถานการณ์ที่ "ความน่าประหลาดใจ" เป็นสัญญาณที่ดีจริง ๆ (เช่น ความจำที่ไม่ได้ถูกอัปเดตนานมาก) และ budget มีจำกัดจริง ๆ `S` ชนะ baseline นั้นชัดเจน ปัญหาคือ `S` ไม่รู้จักใช้ budget ที่เพิ่มขึ้น — ต่อให้ budget เพิ่มเป็น 8 เท่า `S` ก็ยังเก็บความจำจำนวนเท่าเดิม เพราะการตัดสินใจว่าจะจำอะไรถูกกำหนดด้วยเกณฑ์ตายตัว ไม่ผูกกับ budget ที่มีอยู่เลย — เป็นจุดที่รู้แล้วว่าอยู่ตรงไหน แต่ยังไม่ได้แก้ในรอบนี้ (การแก้ตอนนี้เท่ากับ "ปรับ policy หลังเห็นว่ามันแพ้" ซึ่งผิดกฎของโปรเจกต์)

นี่คือผลที่รายงานตรงไปตรงมา — โปรเจกต์นี้ตั้งกฎไว้ตั้งแต่ต้นว่า **ถ้าตัวเลขไม่ผ่านเกณฑ์ ให้รายงานตามจริง ห้ามปรับตัวเลขหรือ "โกง" ให้ผ่าน แล้วให้หยุด** เพราะการรู้เร็วว่าแนวคิดใช้ไม่ได้ (หรือใช้ได้แค่บางกรณี) ดีกว่าไปเสียเวลาสร้างระบบเต็มแล้วมาพบทีหลัง

ทิศทางถัดไป (จะแก้ต่อ, จะยอมรับผลนี้แล้วหยุด, หรือจะออกแบบการทดลองใหม่) เป็นการตัดสินใจของเจ้าของโปรเจกต์ ไม่ใช่สิ่งที่ระบบอัตโนมัติควรตัดสินใจเอง — รายละเอียดทั้งหมดอยู่ใน `plan.md`

## โครงสร้างโปรเจกต์

```
target_SomaOS.md   → เอกสารหลัก อ่านก่อนอ่านอื่นใด
plan.md             → สถานะล่าสุด + ผลตัดสินใจที่ต้องรอเจ้าของโปรเจกต์
plans/              → แผนงานแบบละเอียด (มีเกณฑ์ตัดสินใจที่ล็อกไว้แล้ว ไม่ให้เปลี่ยนเงียบ ๆ)
somaos/broker/      → ตัวคำนวณคะแนนความจำ + ตัวจัดสรรพื้นที่ + policy ต่าง ๆ ที่เอาไว้เปรียบเทียบกัน
somaos/bench/       → ตัวสร้างข้อมูลจำลองสำหรับทดสอบ + ตัวรันการทดลอง + ตัวออกรายงานผล
tests/              → ชุดทดสอบอัตโนมัติ (360 เคส ผ่านทั้งหมด)
```

## วิธีรัน

ต้องมี Python 3.11 ขึ้นไป

```bash
# ติดตั้ง
pip install -e ".[dev]"

# รันชุดทดสอบทั้งหมด
pytest -q

# รันการทดลองขนาดเล็ก (ไม่กี่วินาที เอาไว้เช็คว่าระบบทำงานได้)
python -m somaos.bench.runner --config somaos/bench/configs/smoke.json --out runs

# รันการทดลองขนาดกลาง (ใช้เวลาราว 3-5 นาที ได้ผลที่มีความหมายจริง)
python -m somaos.bench.runner --config somaos/bench/configs/pilot.json --out runs --jobs 8

# รันการทดลองเต็มรูปแบบ (ใช้เวลาราว 10-25 นาทีขึ้นกับจำนวน CPU — ผลที่ใช้ตัดสิน gate จริง)
python -m somaos.bench.runner --config somaos/bench/configs/phase0.json --out runs --jobs 12

# สร้างรายงานสรุปผล (อ่านง่าย บอกผ่าน/ไม่ผ่านชัดเจน)
python -m somaos.bench.report --in runs --out runs/report.md
```

ผลลัพธ์จะอยู่ในโฟลเดอร์ `runs/` — บรรทัดแรกของรายงานจะบอกตรง ๆ ว่า `PHASE0 GATE: PASS` หรือ `PHASE0 GATE: FAIL`

## กติกาการทำงานต่อ (สำหรับใครมาต่อยอด)

- อ่าน `target_SomaOS.md`, `CLAUDE.md`, และ `plan.md` ก่อนเสมอ — `plan.md` มีคำถามที่รอเจ้าของโปรเจกต์ตัดสินใจอยู่
- ตอนนี้แตะได้แค่ `somaos/broker/` กับ `somaos/bench/` เท่านั้น — **ห้ามสร้าง** ส่วนอื่นของระบบ (เช่น kernel, cortex) จนกว่าจะมีการสั่งเปิด phase ถัดไปอย่างชัดเจน
- ห้ามปรับตัวเลข/เกณฑ์/พฤติกรรม policy เพื่อให้ผลการทดลองออกมาดูดีหลังเห็นว่ามันแพ้ — ถ้าผลไม่ดี ให้รายงานตามจริงแล้วช่วยกันคิดว่าทำไม
