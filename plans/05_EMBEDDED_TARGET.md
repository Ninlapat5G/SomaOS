## 1. ทำไมข้อนี้ถึงเปลี่ยนน้ำหนักของทั้งดีไซน์

บนเครื่องทั่วไป ที่เก็บเหลือเฟือ ความทรงจำหนึ่งชิ้นเต็มความคมกิน 1 KB
ชีวิต 200 วันในโลกทดสอบใช้ 490 KB — ดิสก์ 100 GB รองรับได้เป็นร้อยปี
**บันไดการเจือจางแทบไม่มีโอกาสทำงานเลย** และถ้ามองแค่ระบอบนี้
มันก็เป็นแค่ฟีเจอร์กันเหนียวที่ไม่ค่อยได้ใช้

บน microcontroller ทุกอย่างกลับด้าน flash เป็นหน่วย MB, SRAM เป็นหน่วย KB
และทั้งสองอย่างต้องแบ่งกับ firmware **บันไดการเจือจางกลายเป็นสิ่งที่ทำให้ระบบเป็นไปได้เลย
ไม่ใช่ตาข่ายนิรภัย** — และนั่นคือเหตุผลที่ D2 (binary) ถูกวางไว้ในบันไดตั้งแต่ต้น

## 2. บันไดคิดเป็นความจุเท่าไหร่

`nbytes()` วัดที่ `DEFAULT_DIM = 256`:

| ขั้น | ไบต์ต่อความทรงจำ | ทำลายอะไร |
|---|---|---|
| D0_EXACT | 1024 | — |
| D1_INT8 | 256 | ความละเอียดของแต่ละมิติ |
| D2_BINARY | 32 | ขนาด เหลือแต่ทิศทางหยาบ |
| D3_MERGED | 0 | ตัวตนแยก ยุบเข้ากลุ่มแม่ |
| D4_COUNTER | 0 | เวกเตอร์ เหลือแต่ว่าเคยมี |

ชิปจริง (ส่วนแบ่ง flash ที่ให้ store เป็นการประมาณ ไม่ใช่การวัด — เขียนไว้ให้เถียงได้):

| ชิป | flash | SRAM | store | D0 | D1 | D2 |
|---|---|---|---|---|---|---|
| STM32F401 | 512 KB | 96 KB | 256 KB | 256 | 1,024 | **8,192** |
| nRF52840 | 1 MB | 256 KB | 512 KB | 512 | 2,048 | **16,384** |
| RP2040 / Pico | 2 MB | 264 KB | 1.5 MB | 1,536 | 6,144 | **49,152** |
| ESP32-S3 | 8 MB | 512 KB | 6 MB | 6,144 | 24,576 | **196,608** |
| ESP32-S3 N16R8 | 16 MB | 512 KB | 12 MB | 12,288 | 49,152 | **393,216** |

## 3. คุณภาพที่งบระดับชิป

400 ticks, 3 dev seeds, context 256 tokens, recall_ops 32
(`S` = ต้นไม้ · `B2c` = กองแบนที่บีบแบบสุ่ม ซึ่งเป็น control ตาม N-14)

| store | S แก่น | S รายละเอียด | S นิสัย | S เทียบ/คำถาม | B2c แก่น | B2c รายละเอียด | B2c เทียบ/คำถาม |
|---|---|---|---|---|---|---|---|
| 64 KB | **0.981** | 0.456 | 0.934 | **148** | 0.825 | 0.225 | 596 |
| 128 KB | **0.981** | 0.738 | 0.934 | **144** | 0.774 | 0.420 | 596 |
| 256 KB | **0.981** | 0.918 | 0.934 | **149** | 0.764 | 0.687 | 596 |
| 512 KB | **0.981** | 0.910 | 0.934 | **150** | 0.764 | 0.901 | 596 |
| 1.5 MB | **0.981** | 0.935 | 0.934 | **147** | 0.764 | **1.000** | 596 |

อ่านตารางนี้ให้ตรง:

- **แก่นเรื่องนิ่งที่ 0.981 ตลอด** ตั้งแต่ 64 KB ถึง 1.5 MB — 24 เท่าของงบ ไม่ขยับเลย
  นี่คือคุณสมบัติที่ทำให้ MCU ใช้งานได้จริง: agent บนชิปยัง "รู้ว่าเรื่องนั้นเกี่ยวกับอะไร" เสมอ
- **รายละเอียดคือสิ่งที่ซื้อด้วยงบ** 0.456 → 0.935
- **ช่องว่างกว้างขึ้นเมื่องบเล็กลง** ที่ 64 KB ต้นไม้นำ B2c เรื่องแก่น 0.981 vs 0.825
  และเรื่องรายละเอียด 2 เท่า — ยิ่งบีบ โครงสร้างยิ่งได้เปรียบ
- **ที่ 1.5 MB `B2c` ชนะเรื่องรายละเอียด (1.000 vs 0.935)** — ต้องพูดตรง ๆ
  เมื่อมีที่พอจนไม่ต้องเลือก การเก็บทุกอย่างคมย่อมตอบรายละเอียดได้ดีกว่า
  แต่จ่ายด้วยการเทียบ 596 ครั้งต่อคำถาม เทียบกับ 147 — **4 เท่า** ซึ่งบน MCU คือเวลาและไฟ

## 4. RAM: สิ่งที่ต้องอยู่ใน SRAM

store อยู่ใน flash แล้วอ่านทีละ node ได้ แต่ frontier ของการเดินต้องอยู่ใน RAM
วัดจำนวนที่อยู่มากที่สุดที่การนึกหนึ่งครั้งถือไว้พร้อมกัน (ที่อยู่ละ 20 ไบต์):

| recall_ops | ที่อยู่สูงสุด | ไบต์ |
|---|---|---|
| 4 | 15 | 300 |
| 8 | 30 | 600 |
| 16 | 60 | 1,200 |
| 32 | 83 | **1,660** |
| 64 | 83 | **1,660** |

**กรณีแย่ที่สุด 1.7 KB** เทียบกับ SRAM ที่น้อยที่สุดในตาราง (96 KB) = **1.7%**

และที่สำคัญกว่าตัวเลข: **มันอิ่มตัว** ที่ 480 ticks peak = 61 ที่ 960 ticks peak = 61 เท่าเดิม
ทั้งที่ความทรงจำเพิ่มขึ้นเท่าตัว เพราะ frontier ถูกจำกัดด้วย `ops × beam` ไม่ใช่ด้วยขนาด store
— `tests/test_embedded_fit.py::test_working_set_saturates_instead_of_growing_with_the_store`
คุมข้อนี้ไว้ และอีกข้อคุมขอบบน `entries + ops × beam` แบบตายตัว

## 5. ทำไม D2 ถึงเป็น encoding ปกติของ MCU ไม่ใช่สภาพเสื่อม

การเทียบเวกเตอร์ D0 คือคูณ float 256 ครั้ง บนชิปที่**ไม่มี FPU** (Cortex-M0/M0+)
float ทุกตัวถูก emulate ด้วย software

การเทียบเวกเตอร์ D2 คือ XOR 32 ไบต์แล้วนับบิต — จำนวนเต็มล้วน ไม่มี float

นี่คือความต่างระหว่างทำได้กับทำไม่ได้ ไม่ใช่แค่เร็วกว่า
และมันเป็นเหตุผลเชิงวิศวกรรมที่หนุนเหตุผลเชิงการวัดที่ทำให้เลือก binary ตั้งแต่แรก
(§3.3 ของ `03_MEMORY_ARCHITECTURE.md`: recall@10 ตก แต่ gist อยู่ 0.79–1.00)

**ยังไม่ได้วัด cycle count จริง** ข้อนี้เป็นการให้เหตุผลจากสถาปัตยกรรมชิป ไม่ใช่ benchmark
ห้ามอ้างตัวเลขความเร็วจนกว่าจะมีของจริง

## 6. สิ่งที่ยังไม่จริง — พูดให้ชัด

ตัวเลขทั้งหมดข้างบนคือ **งบไบต์และงบ RAM ของดีไซน์** ไม่ใช่การ port

- implementation ปัจจุบันคือ **Python + numpy** ซึ่งรันบน MCU ไม่ได้
- ยังไม่มี C/Rust port ยังไม่มี flash wear levelling ยังไม่มีการวัดไฟ
- ยังไม่ได้ตอบว่า LLM จะอยู่ตรงไหน — บนชิปเล็กคงต้องเป็น host ภายนอกหรือโมเดลจิ๋วมาก
  ซึ่งแปลว่า fast path (เดินเองโดยไม่ถาม LLM) ยิ่งสำคัญบน MCU มากกว่าบน PC
- ส่วนแบ่ง flash ในตาราง §2 เป็นการประมาณ ไม่ใช่การวัดจากโปรเจกต์จริง

**สิ่งที่พิสูจน์แล้ว:** ดีไซน์นี้พอดีกับงบของชิปพวกนี้ และยังตอบคำถามได้ที่งบเท่านั้น
**สิ่งที่ยังไม่พิสูจน์:** โค้ดนี้รันบนชิปพวกนั้น

## 7. สิ่งที่ต้องทำต่อ ถ้าจะเอาจริง

| งาน | ทำไม |
|---|---|
| กำหนด on-flash format ที่อ่านทีละ node ได้ | ตอนนี้ tree อยู่ใน RAM ทั้งต้น |
| port core ไป C หรือ Rust แบบไม่มี allocator | MCU ไม่มี GC และ heap แตกง่าย |
| ทำ D2 เป็น encoding ตั้งต้น ไม่ใช่ปลายทางของบันได | จะได้ไม่ต้องผ่าน D0 ก่อน |
| วัด cycle และไฟจริงบนบอร์ด | §5 ยังเป็นการให้เหตุผล ไม่ใช่ตัวเลข |
| ตัดสินว่า LLM อยู่ที่ไหน | กระทบ interface ทั้งหมด |
