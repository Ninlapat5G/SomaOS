## 0. หลักการที่ทุกอย่างในไฟล์นี้ต้องเคารพ

| # | หลักการ | ผลที่ตามมา |
|---|---|---|
| P1 | **ไม่มีการลบความทรงจำ** | ทุก address ต้อง resolve ได้เสมอ ตลอดอายุของ agent |
| P2 | **"ลืม" = เข้าถึงช้าลง + คมชัดน้อยลง ไม่ใช่หายไป** | สองแกนแยกกัน (§3) |
| P3 | **ความรู้ของระบบคือ vector** | engine ตัดสินใจจาก vector เท่านั้น ห้ามอ่านข้อความเพื่อตัดสินใจ |
| P4 | **ข้อความคือเงา ไม่ใช่ต้นฉบับ** | มีไว้ให้คนอ่าน debug/วิจัย และเป็น payload ตอนส่งเข้า context |
| P5 | **การค้นคือการเดิน ไม่ใช่การสแกน** | ห้ามมี code path ไหนที่ O(N) ต่อการนึกหนึ่งครั้ง |
| P6 | **โครงสร้างต้องแยกตามหน้าที่** | นิสัย / trigger / ทักษะ / ความทรงจำ อยู่คนละที่ คนละกฎ |
| P7 | **ทุกอย่างเป็น state machine** | สถานะจำกัด transition จำกัด → เร็ว ตรวจสอบได้ อธิบายได้ |

## 1. หน่วยเก็บ: `MemoryNode`

```python
MemoryNode {
    addr:      bytes32            # content address (Merkle) — §2
    region:    CORE|TRIGGER|SKILL|ARCHIVE
    level:     int                # 0 = ใบ (คมชัดสุด) ; สูงขึ้น = แก่นขึ้น

    # ── ความรู้จริงของระบบ (P3) ───────────────────────────
    vec:       ndarray            # ★ สิ่งที่ OS ใช้ตัดสินใจ
    dtype:     f32 | i8 | b1      # ระดับการเจือจาง (§3.2)
    dim:       int                # อาจถูกลดเมื่อเจือจางหนัก
    fidelity:  float              # cos(vec_ต้นฉบับ, vec_ปัจจุบัน) ∈ [0,1]

    # ── โครงสร้างต้นไม้ ──────────────────────────────────
    parent:    addr | None
    children:  tuple[addr, ...]
    n_merged:  int                # กี่ความทรงจำถูกยุบรวมอยู่ใน node นี้
    span:      (tick_first, tick_last)

    # ── index เชิงสัญลักษณ์ (สำหรับ exact lookup) ─────────
    keys:      tuple[str, ...]    # entity / topic / trigger key

    # ── สถิติการใช้ (ตัวขับความลึก §3.1) ─────────────────
    stat:      { last_used, use_count, hit_count, miss_count }

    # ── เงาสำหรับมนุษย์ (P4) ─────────────────────────────
    text_ref:  str                # engine ห้ามอ่านเพื่อตัดสินใจ
    raw_refs:  tuple[event_id,..] # provenance กลับไปหา event log
}
```

### ทำไมต้อง vector ไม่ใช่ข้อความ

| | ข้อความ | vector |
|---|---|---|
| เปรียบเทียบความใกล้เคียง | ต้องใช้ LLM หรือ keyword match ที่เปราะ | dot product — เร็ว, มีเมตริก, วัดได้ |
| ยุบรวม (เจือจาง) | ต้องเรียก LLM สรุป = แพง + ไม่ deterministic | centroid = ค่าเฉลี่ย ทำได้ทันที ทำซ้ำได้ |
| วัด "เหลือแก่นเท่าไหร่" | วัดไม่ได้ | `cos(เดิม, ปัจจุบัน)` = ตัวเลข 0..1 |
| ข้ามภาษา / ข้ามสื่อ (ภาพ เสียง) | ทำไม่ได้ | โครงเดิมใช้ได้เลย |
| ขนาด | โตตามความยาว | คงที่ และบีบได้เป็นขั้น (§3.2) |

**นี่คือเหตุผลที่ "เจือจาง" เป็นไปได้จริงเฉพาะบน vector** — บนข้อความ การเจือจางคือการเรียก LLM
สรุปใหม่ ซึ่งแพง ไม่ deterministic และทำลายของเดิม (ซึ่งละเมิด P1)

### กฎเหล็กของข้อความ (บังคับด้วย test)

```
INVARIANT V1 — engine ห้ามอ่าน text_ref เพื่อตัดสินใจ
  ลบ text_ref ทั้งคลังทิ้ง → พฤติกรรมของระบบต้องเหมือนเดิม bit-for-bit
  (ผลลัพธ์ที่ส่งเข้า context จะว่างเปล่า แต่ *เส้นทางการเดินและ node ที่เลือก* ต้องเหมือนเดิมทุกก้าว)

INVARIANT V2 — text_ref แตะได้แค่ 2 ที่
  (1) ขั้น MATERIALIZE ตอนแปลง node เป็น payload เข้า context
  (2) report / debug / งานวิจัย
```

## 2. ที่อยู่: content-addressed แบบ Merkle

```
addr(node) = sha256( canonical(vec_bytes ‖ level ‖ region ‖ sorted(children_addrs)) )
```

| ได้อะไร | ทำไม |
|---|---|
| **Dedupe ฟรี** | ความทรงจำเนื้อหาเดียวกัน = address เดียวกัน เก็บครั้งเดียว |
| **ตรวจความถูกต้องได้** | แม่เปลี่ยนเมื่อลูกเปลี่ยน → snapshot/diff/ตรวจ corruption ได้ทั้งต้นไม้ |
| **Append-only** | เข้ากับ event log ที่เป็น source of truth |
| **Replay ตรงเป๊ะ** | address เดียวกัน = สถานะความจำเดียวกัน ใช้เป็น cache key ได้ |

### ⚠️ ปัญหาที่ตามมาและทางแก้ — `alias table`

เจือจาง = `vec` เปลี่ยน = **address เปลี่ยน** แต่ P1 บอกว่า address เดิมต้อง resolve ได้เสมอ

```
alias : addr_เดิม → addr_ปัจจุบัน        (append-only, ไม่มีการลบ)

resolve(addr) → เดินตาม alias จนถึงตัวที่ยังมีอยู่จริง
              → คืน (node, fidelity)     # บอกด้วยว่าเหลือคมชัดแค่ไหน
```

นี่คือ **page table entry ที่ชี้ไป frame ที่ถูกบีบอัด** ตรง ๆ — คนที่ถือ address เก่าไว้ยังใช้ได้
แค่ได้ของที่หยาบลง `resolve()` **ห้าม return None เด็ดขาด** (มี test คุม)

## 3. "เจือจาง" — สองแกนที่แยกกันโดยสิ้นเชิง

> นี่คือหัวใจของโมเดล และเป็นจุดที่ดีไซน์เก่าไม่มีเลย

| แกน | คืออะไร | ขับด้วย | รู้สึกยังไง |
|---|---|---|---|
| **ความลึก** (depth) | ต้องเดินกี่ก้าวกว่าจะถึง | **ความถี่การใช้** | "นึกออกช้า" / "ติดอยู่ที่ปาก" |
| **ความคมชัด** (fidelity) | เหลือรายละเอียดแค่ไหน | **ความจุคลังเต็ม** | "จำได้ว่ามีเรื่องนี้ แต่จำรายละเอียดไม่ได้" |

**สองแกนนี้อิสระต่อกัน** — ความทรงจำอาจอยู่ตื้นแต่หยาบ (เรื่องที่นึกถึงบ่อยแต่นานมาก),
หรืออยู่ลึกแต่คมชัด (เรื่องสะเทือนใจที่ไม่ได้คิดถึงมานาน) เหมือนคนจริง

### 3.1 แกนความลึก — ต้นไม้แบบ splay

```
ใช้งาน node → เลื่อนขึ้นใกล้ root  (promote)
ไม่ถูกใช้    → จมลงเรื่อย ๆ        (sink, ทุกรอบ consolidation)
```

- ของที่ใช้ทุกวัน → อยู่ชั้น 1-2 → นึกออกทันที
- ของที่ไม่ได้แตะมาเป็นปี → อยู่ชั้น 8-10 → ต้องเดินหลายก้าว (แต่ยังไปถึงได้เสมอ)
- **"ยิ่งเก่า ยิ่งอยู่ลึก" ถูก implement ตรงตัว** และ "ลืม" = ต้นทุนการนึกสูงขึ้น ไม่ใช่ข้อมูลหาย
- ต้นทุนการนึก = `O(depth × beam)` **ไม่ใช่ O(N)** ← ตอบ P5 และแก้ KC3 เชิงออกแบบ

### 3.2 แกนความคมชัด — บันไดเจือจาง 5 ขั้น

ทำงานเมื่อ `store_used > store_budget` เท่านั้น เลือกเหยื่อจาก node ที่ `use_count` ต่ำสุด + ลึกสุด

| ขั้น | กลไก | ขนาดที่เหลือ | ยังตอบอะไรได้ |
|---|---|---|---|
| **D0** | `f32` เต็มมิติ | 100% | รายละเอียดครบ ตอบเจาะจงได้ |
| **D1** | quantize → `int8` | ~25% | เกือบครบ (cos error < 0.02) |
| **D2** | ยุบพี่น้องเป็น centroid ที่ node แม่ | ~1/b | "ช่วงนั้น เรื่องแนวนั้น กับคนนั้น" |
| **D3** | ลดมิติด้วย projection ที่ seed คงที่ | ~25% ของ D2 | แก่นกว้าง ๆ |
| **D4** | binary sign vector + ตัวนับ | ~3% | "เคยมีเรื่องแบบนี้อยู่" เท่านั้น |

**ทุกขั้นเป็น deterministic และวัดผลได้:** `fidelity = cos(vec_D0, vec_ปัจจุบัน)`
→ **"เจือจาง" กลายเป็นตัวเลข 0..1 ที่พล็อตเป็นกราฟได้** ซึ่งเป็นสิ่งที่ทำให้วิสัยทัศน์นี้พิสูจน์ได้

**และห้ามลงต่ำกว่า D4** — D4 คือพื้น ความทรงจำจะบางลงเรื่อย ๆ แต่ไม่มีวันเป็นศูนย์ (P1)

### 3.3 ขนาดคลังคือ "ขนาดสมอง"

```
store_budget_bytes    # ← ตัวนี้คือ "คนนี้ความจำดีแค่ไหน" กำหนดต่อ agent
```

- ตั้งใหญ่ → ของอยู่ที่ D0/D1 นาน → จำรายละเอียดได้เยอะ
- ตั้งเล็ก → ของที่ไม่ค่อยใช้ไหลลง D2/D3/D4 เร็ว → **แก่นอยู่ รายละเอียดหาย**
- **ทุก policy ต้องอยู่ใต้ `store_budget` เดียวกันตอน benchmark** ← แก้ความไม่ยุติธรรมของรอบเก่า

## 4. สี่ภูมิภาคของความจำ (P6)

> สมองไม่ได้เก็บนิสัยไว้ที่เดียวกับความทรงจำเมื่อวาน — ระบบนี้ก็ต้องไม่เก็บ

```
┌──────────────────────────────────────────────────────────────────────┐
│ CORE     ตัวตน · นิสัย · ค่านิยม · วิธีพูด                            │
│          → อยู่ใน context ทุกครั้งที่รัน ไม่ต้องเรียก                  │
│          → OS: kernel-resident pinned pages                          │
│          → ห้ามเจือจาง ห้ามจม  ★                                     │
├──────────────────────────────────────────────────────────────────────┤
│ TRIGGER  กี่โมงทำอะไร · เกิด event อะไรแล้วทำอะไร                     │
│          → ไม่กิน context เลย นอนรออยู่ใน index                       │
│          → OS: interrupt vector table + timer wheel                  │
│          → ห้ามเจือจาง  ★                                            │
├──────────────────────────────────────────────────────────────────────┤
│ SKILL    วิธีทำ · เคยทำแบบนี้แล้วได้ผล · ขั้นตอน                      │
│          → ดึงเมื่อ "สถานการณ์" ตรง (ไม่ใช่เมื่อ "หัวข้อ" ตรง)         │
│          → OS: demand-paged code pages                               │
│          → เจือจางได้ถึง D2 (เหลือ "เคยทำเรื่องแนวนี้")               │
├──────────────────────────────────────────────────────────────────────┤
│ ARCHIVE  ประสบการณ์ · เหตุการณ์ · ความรู้ที่กลั่นแล้ว                  │
│          → ต้องเรียกถึงจะมา — ที่นี่คือต้นไม้ splay ของจริง            │
│          → OS: paged memory + multi-level page table                 │
│          → เจือจางได้ถึง D4                                          │
└──────────────────────────────────────────────────────────────────────┘
```

★ **`CORE` และ `TRIGGER` ห้ามเจือจางเด็ดขาด** — นิสัยไม่เลือนเพราะความจำเต็ม และความตั้งใจ
ไม่หายเพราะที่ไม่พอ ถ้าสองอันนี้เจือจางได้ ตัวตนของ agent จะไม่นิ่ง ซึ่งทำลายทุกอย่าง
→ ทั้งสองมี **hard quota แยก** ที่ถูกกันไว้ก่อน แล้วที่เหลือค่อยเป็นของ `SKILL`/`ARCHIVE`

### งบประมาณสามก้อน (คนละสกุลเงิน — อย่าปนกัน)

```
context_budget_tokens   # RAM   — token ที่ส่งเข้าโมเดลต่อครั้ง
store_budget_bytes      # Disk  — ขนาดคลังทั้งหมด = "ขนาดสมอง"
recall_ops_budget       # เวลา  — จำนวนก้าวที่เดินได้ต่อการนึกหนึ่งครั้ง
```

**การมี `recall_ops_budget` คือสิ่งที่ทำให้ต้นไม้มีค่าในกระดานคะแนน** — ถ้าการสแกนทั้งคลังยังฟรี
เหมือนรอบเก่า ต่อให้เขียนต้นไม้ที่สมบูรณ์แบบ ตัวเลขก็ไม่ขยับ

### แล้ว CORE/SKILL มาจากไหน — การตกผลึกนิสัย

`CORE` ไม่ได้ถูกเขียนด้วยมือทั้งหมด มันเกิดจากการที่ pattern เดิม ๆ ถูกยืนยันซ้ำจนขึ้นถึงยอด:

```
ARCHIVE (เหตุการณ์ซ้ำ ๆ)  --ยืนยัน n ครั้ง, สม่ำเสมอ-->  SKILL/CORE (นิสัย)
```

- เกณฑ์: `n_merged ≥ N` **และ** ลูกกระจายตัวต่ำ (cos ระหว่างลูกสูง = "ทำแบบนี้ทุกครั้งจริง")
- นี่คือ "ประสบการณ์ตกผลึกเป็นนิสัย" — และเป็น **deterministic ล้วน** ไม่ต้องใช้ LLM
- ทางกลับกันมีด้วย: นิสัยที่ถูกขัดบ่อย ๆ จะถูกลดชั้นกลับลง `ARCHIVE`

## 5. State machine

### 5.1 FSM ของการนึก (`ARCHIVE` / `SKILL`)

```
        ┌──────┐
        │ IDLE │
        └───┬──┘
      perceive / query
            ▼
        ┌──────┐   สร้าง cue vector จากสิ่งเร้า
        │ CUE  │
        └───┬──┘
            ├──── hit CORE/TRIGGER ──────────────┐  O(1) ไม่ต้องเดิน
            ▼                                    │
    ┌───────────────┐  descend / ascend / lateral│
    │   NAVIGATE    │◄──────────┐                │
    └───────┬───────┘           │                │
            │ ─── ก้าวต่อ ───────┘                │
            ▼                                    ▼
      ┌─────────────┐                    ┌──────────────┐
      │ MATERIALIZE │◄───────────────────┤  RESIDENT    │
      └──────┬──────┘  แปลง node → payload└──────────────┘
             ▼         (จ่าย token ตรงนี้ที่เดียว)
      ┌─────────────┐
      │   SETTLE    │  promote node ที่ใช้ (splay) · อัปเดตสถิติ · บันทึกเส้นทาง
      └──────┬──────┘
             ▼  IDLE
```

**transition ที่ agent เลือกได้ (เปิดเป็น tool):**

| tool | ความหมาย | ต้นทุน |
|---|---|---|
| `descend(k)` | เจาะลงหาที่ละเอียดขึ้น | 1 op + อ่าน k centroid |
| `ascend()` | ถอยขึ้นหาแก่นที่กว้างขึ้น | 1 op |
| `lateral(k)` | เดินข้างไปเรื่องที่เชื่อมโยงกัน | 1 op + อ่าน k |
| `materialize(addr)` | ดึงเข้า context จริง | token ตามขนาด |
| `stop()` | พอแล้ว | 0 |

- **engine เป็นคนเดินและตรวจ agent เป็นคนเลือกทิศ** — เกินโควตา `recall_ops_budget` ระบบตัดเอง
- **เส้นทางที่เดินถูกบันทึกทุกก้าว → `explain()` ได้ฟรี** ไม่ต้องสร้างระบบ trace แยก
- **fast path ที่ไม่แตะ LLM ต้องมีเสมอ**: greedy descend ตาม cosine — ใช้ตอน agent ไม่เรียก tool
  หรือตอน model bus ล่ม (§GATE degradation)

### 5.2 FSM ของ `TRIGGER`

```
ARMED ──(เงื่อนไขตรง)──► FIRED ──(ทำแล้ว)──► ARMED (ถ้าซ้ำได้) หรือ RETIRED
  ▲                                              │
  └──────────────(ตั้งใหม่)───────────────────────┘
```

| ชนิด | เก็บยังไง | ต้นทุนการเช็ค |
|---|---|---|
| ตามเวลา ("ทุกเช้า 8 โมง") | timer wheel เรียงตาม tick | O(1) ต่อ tick |
| ตาม event ("ถ้าเจอ X ให้ทำ Y") | hash bucket ตาม event key | O(1) ต่อ event |
| ตามเงื่อนไข ("ถ้า mood < k") | ตรวจตอน tick กับ predicate ที่ compile แล้ว | O(จำนวน trigger ที่ armed) |

**ไม่ใช่การค้นหา** — trigger คือ interrupt ไม่ใช่ retrieval นี่คือ moat ที่ยังไม่มีใครทำ

### 5.3 FSM ของ node (วงจรชีวิตความทรงจำ)

```
     NEW ──► HOT ⇄ WARM ⇄ COLD ──► DILUTED(D1..D4) ──► MERGED(อยู่ในแม่)
              │                                              │
              └──────────── ถูกเรียกใช้อีก ────────────────────┘
                        (ตื้นขึ้น แต่ fidelity ไม่กลับมา)
```

**ข้อสังเกตสำคัญ: การเจือจางเป็นทางเดียว** — นึกถึงอีกครั้งทำให้ *เข้าถึงง่ายขึ้น* แต่
*รายละเอียดที่หายไปแล้วไม่กลับมา* ตรงกับสมองคนพอดี และตรงกับ §5.6 ของ north star
ที่ห้าม reconstructive recall แบบแต่งเติมของเดิม

## 6. การวัด — ทิศทางใหม่ทั้งหมด

> เมื่อ agent เลือกเองได้ (LLM อยู่ในลูป) การวัดแบบ "policy ของเราตัดสินใจถูกกว่า" ใช้ไม่ได้แล้ว
> **ทางออก: เลิกวัดว่าตัดสินใจถูกไหม แล้วหันไปวัด "รูปร่างความสามารถ" ของระบบความจำแทน**
> ทุกตัวข้างล่างวัดได้แม้ LLM จะเลือกเอง เพราะมันเป็นสมบัติของ *โครงสร้าง* ไม่ใช่ของ *การตัดสินใจ*

### M1 — เส้นโค้งความจุ ★ ตัวชี้ขาดใหม่

```
แกน x = store_budget_bytes (เล็ก → ใหญ่)
แกน y = คะแนน 2 เส้นแยกกัน:  รายละเอียด (detail)  และ  แก่น (gist)
```

**ลายเซ็นที่ต้องเห็นถ้าดีไซน์ถูก:** เส้น detail ลาดลงเรื่อย ๆ แต่ **เส้น gist แบนเกือบตลอด**
= "ลืมรายละเอียด แต่พอจำได้" นี่คือวิสัยทัศน์ทั้งหมดของโปรเจกต์ ย่อเป็นกราฟเดียว

**ลายเซ็นของระบบที่ผิด:** สองเส้นตกพร้อมกันเป็นหน้าผา = คลังเต็มแล้วของหายจริง

→ **แทบไม่มีใครในวงการพล็อตกราฟนี้** เพราะระบบส่วนใหญ่ไม่มีแนวคิดเรื่อง "คลังมีขนาด"
   นี่จึงเป็น differentiator ที่วัดเป็นตัวเลขได้ ไม่ใช่คำโฆษณา

### M2 — เส้นโค้ง context

quality เทียบ `context_budget_tokens` ที่คลังเท่ากัน
**ข้ออ้าง:** SomaOS รักษาคุณภาพไว้ได้ที่ context เล็กกว่ามาก เทียบกับ B0 (ยัดหมด) และ B2 (RAG)
= ข้ออ้าง "context ไม่บวม" ที่กลายเป็นตัวเลข

### M3 — ต้นทุนการนึก (deterministic 100% แม้ LLM อยู่ในลูป)

`recall_ops` และ ms ต่อการนึกหนึ่งครั้ง เทียบกับขนาดคลัง
**ข้ออ้าง:** ต้นไม้โตแบบ ~log N ส่วน RAG แบนโตแบบเชิงเส้น → พล็อตที่ N = 10³ → 10⁶

### M4 — ความเสถียรของตัวตน

อัตราการขัดแย้งกับ `CORE` ตลอด session ยาว
เป็นสมบัติของ *โครงสร้าง* (CORE อยู่ใน context เสมอ) ไม่ใช่ของการเลือกของ LLM

### M5 — ความแม่นของ trigger

ยิงตรงเวลา / พลาด / ยิงมั่ว — **ไม่แตะ LLM เลย วัดตรง ๆ ได้ 100%**
ทดสอบ prospective memory ซึ่งเป็น moat ที่ยังไม่มีคู่แข่งเจ้าไหนมี

### M6 — อธิบายได้

% ของคำตอบที่มีเส้นทางการเดินครบถ้วน + ทดสอบ `memory_causality` (ลบ node → คำตอบต้องเปลี่ยน)

### M7 — replay ตรงเป๊ะด้วย VCR

บันทึก output ของ LLM ไว้ → replay ต้องได้ event log เหมือนเดิม bit-for-bit
**ข้ออ้างเรื่อง determinism ยังอยู่** แค่เปลี่ยนจาก "ไม่มี LLM" เป็น "ทำซ้ำได้"
ซึ่งเป็นสิ่งที่ production ต้องการจริง ๆ อยู่แล้ว

### M8 — เทียบภายนอก (ของแถมจากการเลือกข้อ ข.)

LoCoMo / LongMemEval เทียบกับ MemGPT/Letta, Mem0, Zep ด้วยตัวเลขที่วงการยอมรับ
**ดีไซน์เก่าทำข้อนี้ไม่ได้เลยเพราะห้ามมี LLM — การให้ agent เลือกเองปลดล็อกยาร์ดสติ๊กที่แข็งที่สุด**

### OPT oracle ยังใช้ได้ — แค่เปลี่ยนเป้า

เดิม: "ถ้ารู้อนาคต ควรใส่อะไรใน context" → ตอนนี้ agent เลือกเอง วัดแบบเดิมไม่ได้
ใหม่: **"ถ้ารู้อนาคต ควรจัดสรรคลังขนาด M ยังไงให้ตอบได้มากที่สุด"**
→ ยังคำนวณ offline ได้ ยังได้ `competitive_ratio` ที่มีความหมาย และ **โค้ด oracle เดิมใช้ต่อได้**

## 8. สิ่งที่ยังไม่ตัดสิน (ต้องเคาะก่อนเขียนโค้ด)

1. **embedding มาจากไหนใน Phase แรก** — ใช้ hash-based deterministic embedding ที่สร้างเองเพื่อ
   ทดสอบโครงสร้างก่อน (ฟรี เร็ว deterministic) แล้วค่อยเปลี่ยนเป็น embedding จริงทีหลัง?
   หรือใช้ของจริงตั้งแต่แรก? — **ผมแนะนำแบบแรก** เพราะเรากำลังทดสอบ *โครงสร้าง* ไม่ใช่ *คุณภาพ embedding*
   และ interface ต้องออกแบบให้สลับได้ตั้งแต่ต้น
2. **`dim` เท่าไหร่** และบันได quantization ใช้ค่าอะไรจริง ๆ (ต้อง calibrate)
3. **`CORE` เริ่มต้นมาจากไหน** — เขียนมือตอนสร้าง agent (persona เริ่มต้น) แล้วให้ตกผลึกเพิ่มเอง?
4. **branching factor `b` ของต้นไม้** และเกณฑ์แตก/ยุบ node
5. **`SKILL` แยกจาก `CORE` จริงไหม** หรือควรยุบเป็นภูมิภาคเดียว
