## 0. หลักการที่ทุกอย่างต้องเคารพ

| # | หลักการ | ผลที่ตามมา | ที่มา |
|---|---|---|---|
| P1 | **ไม่มีการลบความทรงจำ** | ทุก address ต้อง resolve ได้เสมอ | Bjork: ลืม = เข้าถึงไม่ได้ ไม่ใช่ถูกลบ |

| P7 | **ทุกอย่างเป็น state machine** | สถานะจำกัด → เร็ว ตรวจสอบได้ อธิบายได้ | — |
| P8 | **verbatim ต้องตายก่อน gist เสมอ** | บันไดการเจือจางเดินทางเดียว | Brainerd & Reyna: fuzzy-trace theory |

## 1. หน่วยเก็บ: `MemoryNode`

```python
MemoryNode {
    addr:      bytes32            # content address (Merkle) — §2
    region:    CORE | TRIGGER | SKILL | ARCHIVE
    level:     int                # ชั้นในต้นไม้ (0 = ใบ) — §4.2

    # ── ความรู้จริงของระบบ (P3) ───────────────────────────
    vec:       ndarray            # ★ สิ่งที่ OS ใช้ตัดสินใจ
    grade:     D0 | D1 | D2 | D3 | D4     # ขั้นการเจือจาง — §3.2
    fidelity:  float              # cos(vec_D0, vec_ปัจจุบัน) ∈ [0,1] — ลดทางเดียว

    # ── โครงสร้างต้นไม้ ──────────────────────────────────
    parent:    addr | None
    children:  tuple[addr, ...]
    n_merged:  int                # กี่ความทรงจำถูกยุบรวมอยู่ใน node นี้
    span:      (tick_first, tick_last)

    # ── index เชิงสัญลักษณ์ (exact lookup, ไม่ใช่ similarity) ─
    keys:      tuple[str, ...]    # entity / topic / cue ของสถานการณ์ / trigger key

    # ── สถิติการใช้ (ขับแกนความลึก §3.1) ─────────────────
    stat:      { last_used, use_count, hit_count, miss_count }

    # ── เงาสำหรับมนุษย์ (P4) ─────────────────────────────
    text_ref:  str                # engine ห้ามอ่านเพื่อตัดสินใจ
    raw_refs:  tuple[event_id,..] # provenance กลับไปหา event log
}
```

### ทำไมต้อง vector ไม่ใช่ข้อความ

| | ข้อความ | vector |
|---|---|---|
| เปรียบเทียบความใกล้เคียง | ต้องใช้ LLM หรือ keyword match ที่เปราะ | dot product — เร็ว มีเมตริก วัดได้ |
| **ยุบรวม (เจือจาง)** | **ต้องเรียก LLM สรุป = แพง ไม่ deterministic และทำลายของเดิม** | centroid = ค่าเฉลี่ย ทำทันที ทำซ้ำได้ |
| วัด "เหลือแก่นเท่าไหร่" | **วัดไม่ได้** | `cos(เดิม, ปัจจุบัน)` = ตัวเลข 0..1 |
| ข้ามภาษา / ภาพ / เสียง | ทำไม่ได้ | โครงเดิมใช้ได้เลย |
| ขนาด | โตตามความยาว | คงที่ และบีบเป็นขั้นได้ (§3.2) |

**บนข้อความ "เจือจาง" ทำไม่ได้จริง** — มันกลายเป็นการเรียก LLM เขียนใหม่ ซึ่งละเมิด P1

### กฎเหล็กของข้อความ (บังคับด้วย test)

```
INVARIANT V1 — engine ห้ามอ่าน text_ref เพื่อตัดสินใจ
  ลบ text_ref ทั้งคลัง → เส้นทางการเดินและ node ที่ถูกเลือก เหมือนเดิม bit-for-bit
INVARIANT V2 — text_ref แตะได้แค่ 2 ที่: ขั้น MATERIALIZE และ report/debug
```

## 2. ที่อยู่: content-addressed แบบ Merkle

```
addr(node) = sha256( canonical(vec_bytes ‖ grade ‖ level ‖ region ‖ sorted(children_addrs)) )
```

| ได้อะไร | ทำไม |
|---|---|
| **Dedupe ฟรี** | เนื้อหาเดียวกัน = address เดียวกัน เก็บครั้งเดียว |

เจือจาง = `vec` เปลี่ยน = **address เปลี่ยน** แต่คนที่ถือ address เก่าต้องยังใช้ได้

```
              → คืน (node, fidelity)     # บอกด้วยว่าเหลือคมชัดแค่ไหน
              # ห้ามคืน None เด็ดขาด
```

## 3. "เจือจาง" — สองแกนที่แยกกันโดยสิ้นเชิง

> ตรงกับ Bjork & Bjork (1992) ที่แยก **retrieval strength** ออกจาก **storage strength**
> — สองค่าที่อิสระต่อกัน และการลืมคือ retrieval strength ตก ไม่ใช่การลบ

| แกน | คืออะไร | ขับด้วย | รู้สึกยังไง | เทียบ Bjork |
|---|---|---|---|---|
| **ความลึก** | เดินกี่ก้าวถึง | **ความถี่การใช้** | "นึกออกช้า / ติดอยู่ที่ปาก" | retrieval strength |
| **ความคมชัด** | เหลือรายละเอียดแค่ไหน | **ความจุคลังเต็ม** | "จำได้ว่ามีเรื่องนี้ แต่จำรายละเอียดไม่ได้" | storage strength* |

\* ดู `04_HUMAN_MEMORY_BASIS.md` §9 ข้อ 1 — ในคนแทบไม่เสื่อม ในเราเสื่อมได้เพราะมีขีดจำกัดเป็นไบต์จริง **ต้องพูดให้ชัดตอนรายงาน**

**สองแกนอิสระกัน** — อาจอยู่ตื้นแต่หยาบ (เรื่องที่คิดถึงบ่อยแต่นานมาก) หรือลึกแต่คม
(เรื่องสะเทือนใจที่ไม่ได้แตะมานาน) เหมือนคนจริง

### 3.1 แกนความลึก — ต้นไม้แบบ splay

```
ใช้งาน node → เลื่อนขึ้นใกล้จุดเข้า (promote)
ไม่ถูกใช้    → จมลงเรื่อย ๆ         (sink, ทุกรอบ consolidation)
```
- ของที่ใช้ทุกวันอยู่ชั้นตื้น → นึกออกทันที · ของที่ไม่แตะมาเป็นปีอยู่ลึก → ต้องเดินหลายก้าว แต่**ไปถึงได้เสมอ**
- ต้นทุนการนึก = `O(depth × beam)` **ไม่ใช่ O(N)** (P5)
- **การดึงกลับทำให้ตื้นขึ้น แต่ไม่ทำให้คมขึ้น** — ตรงกับ Bjork (retrieval ยกเฉพาะ retrieval strength)

### 3.2 ★ แกนความคมชัด — บันได 5 ขั้น (แก้ใหม่ตามผลวัด)

> **⚠️ แก้จาก v2.0** ร่างแรกใส่ "ลดมิติด้วย random projection" เป็นขั้นหนึ่ง และวาง binary ไว้ท้ายสุด
> **ทั้งสองอย่างผิด** — วัดแล้ว (`somaos/bench/experiments/quantization_fidelity.py`) ดู §3.3

ทำงาน**เมื่อ `store_used > store_budget` เท่านั้น** เลือกเหยื่อจาก `use_count` ต่ำสุด + ลึกสุด

| ขั้น | กลไก | bytes/node (dim=256) | ตอบ "ชิ้นไหน" ได้ | ตอบ "แนวไหน" ได้ |
|---|---|---|---|---|
| **D0** | `float32` | 1024 | ✅ | ✅ |
| **D1** | scalar quantize → `int8` | 256 (**4×**) | ✅ (recall@10 ≈ 0.98–0.996) | ✅ |
| **D2** | sign bits → `binary` | 32 (**32×**) | ❌ (recall@10 ≈ 0.21–0.74) | ✅ (0.79–1.00) |
| **D3** | ยุบเข้าแม่ (แม่รับน้ำหนัก+ช่วงเวลา) | ~0 (+alias) | ❌ ตัวตนหายไปในกลุ่ม | ✅ (แม่ยังชี้กลุ่มถูก ~1.00) |
| **D4** | เหลือตัวนับที่บรรพบุรุษ | ~0 | ❌ | "เคยมีเรื่องแบบนี้ n ครั้ง ช่วงนั้น" |

**ลำดับนี้ไม่ได้เรียงตามขนาด แต่เรียงตาม *อะไรที่ถูกทำลาย*** — D0→D2 เสียความคมของ **verbatim**
ก่อน แล้ว D3→D4 ค่อยเสีย **ตัวตนเชิงโครงสร้าง** ตรงกับ P8 (fuzzy-trace: verbatim ตายก่อน gist)

**D4 คือพื้น ห้ามต่ำกว่านี้** (P1)

### 3.3 ★ ทำไมถึงเลือก binary — คำตอบที่วัดมาแล้ว ไม่ได้เดา

รันได้เอง: `python -m somaos.bench.experiments.quantization_fidelity`
(dim=256, คลัง 8,000 ชิ้น, 300 query ต่อเงื่อนไข, คลังแบบ cluster ที่ความหนาแน่นต่างกัน 4 แบบ)

| เงื่อนไข | `recall@10` int8 | `recall@10` **binary** | ชี้ถูก cluster (gist) int8 | **binary** |
|---|---|---|---|---|
| 50 cluster, σ=0.6 | 0.979 | **0.214** | 1.000 | **1.000** |
| 200 cluster, σ=0.9 | 0.993 | **0.483** | 1.000 | **1.000** |
| 500 cluster, σ=1.2 | 0.996 | **0.738** | 1.000 | **1.000** |
| 1000 cluster, σ=1.5 | 0.993 | **0.428** | 1.000 | **0.787** |

> **ข้อสรุป: binary ทำลาย "ชิ้นไหนกันแน่" แต่รักษา "มันเป็นเรื่องแนวไหน" ไว้เกือบครบ**

**นี่ไม่ใช่ผลข้างเคียง — มันคือเหตุผลที่เลือก** เพราะสิ่งที่ binary ทำลายคือสิ่งที่ *ควร* ถูกทำลายก่อน
พอดี (verbatim) และสิ่งที่มันรักษาไว้คือสิ่งที่ *ควร* อยู่รอด (gist) = fuzzy-trace theory ที่ implement เป็นไบต์

**ฐานทางทฤษฎี:** sign bits คือ SimHash (Charikar 2002) — โอกาสที่บิตตรงกันเป็นฟังก์ชันของมุมโดยตรง
`P[bits agree] = 1 − θ/π` ดังนั้น Hamming distance เป็น **ตัวประมาณ cosine แบบไม่เอนเอียง**
ที่ความแปรปรวนลดลงตามจำนวนบิต → **บิต = ขนาดตัวอย่างของการประมาณมุม**

**ผลที่ตามมาทันที และเป็นเหตุผลที่ตัด "ลดมิติ" ทิ้ง:**
ลดมิติก่อน binary = ลดจำนวนบิต = **ลดขนาดตัวอย่าง** → การประมาณมุมพังเร็วกว่าที่ประหยัดได้
วัดแล้วเห็นชัด (dim 64 แย่กว่า dim 256 อย่างเป็นระบบ) → **ในบันไดนี้จึงไม่มีการลดมิติเลย**

### ⚠️ ข้อจำกัดของตัวเลขชุดนี้ที่ต้องรายงานคู่กันเสมอ
- คลังเป็น **Gaussian cluster สังเคราะห์** ซึ่งใจดีกว่า embedding จริง (ที่ covariance ไม่สมมาตร
  และเป็นตัวแปรที่มีงานวิจัยชี้ว่ากระทบคุณภาพ binary quantization โดยตรง)
- ตัวเลขจริงจะต่ำกว่านี้ → **ต้องวัดซ้ำบน embedding จริงที่ Phase 0.5**
- สิ่งที่เชื่อถือได้คือ **รูปแบบ** (ขั้นไหนฆ่าคำถามแบบไหน) ไม่ใช่ทศนิยมตำแหน่งที่สาม

### 3.5 ⚠️ D3 ไม่แตะเวกเตอร์ของแม่ (แก้จาก v2.1)

ร่างเดิมให้ D3 **เฉลี่ยลูกเข้า centroid ของแม่** ฟังดูถูก แต่วัดแล้ว**ไม่ได้อะไรเลย** —
แม่อยู่ตรงกลาง cluster ของตัวเองอยู่แล้ว ผลวัดใน §3.3 แสดงว่าแม่ชี้กลุ่มถูก ~1.00 ทั้งเฉลี่ยและไม่เฉลี่ย

**สิ่งที่การเฉลี่ยซื้อมาคือ: address ของบรรพบุรุษเปลี่ยนทุกครั้งที่มีการยุบ** และตามมาด้วย
alias chain ที่ยาวขึ้นเรื่อย ๆ, การชนกันของ address ระหว่าง node กับลูกหลานของตัวเอง (= node เป็นพ่อของตัวเอง),
และ loop เก็บกวาดที่ไม่มีวันจบ — เจอตอนรัน `agent_life.py` 200 วัน

→ **ยกเลิก** ตอนนี้ D3 แค่ปลดลูกออก แล้วแม่บันทึกว่า “ตอนนี้ฉันแทนของมากขึ้น”
ผ่าน `n_merged` และ `span` ซึ่ง**อยู่นอก content address** จึงบันทึกได้โดยแม่ไม่กลายเป็นคนละ node
D4 ต่างตรงที่ไม่เพิ่มน้ำหนัก เพิ่มแต่ตัวนับ — “จางเกินกว่าจะเป็นหลักฐานเรื่องอะไรนอกจากว่ามันเคยมี”

> บทเรียน: **ความซับซ้อนที่แลกความถูกต้องมาโดยไม่คืนอะไรที่วัดได้ ไม่ใช่ trade-off**

### 3.6 การนึกซ้ำต้านการเจือจาง (ใหม่)

`retrieval_strength` **เสื่อมตามเวลา** ดังนั้นการเรียงเหยื่อด้วยมันอย่างเดียวทำให้
ความทรงจำที่ถูกนึกถึงสิบกว่าครั้ง**ถูกยุบทิ้ง**เมื่อของรอบตัวหมดไปแล้ว — ตรงข้ามกับที่ควรเป็นภายใต้แรงกดดัน

`use_count` **ไม่เสื่อม** ในภาษาของ Bjork นั่นคือ **storage strength** และการดึงกลับมาใช้ทำให้มันเพิ่ม
(testing effect) → ตอนนี้ `use_count` นำหน้าในการเรียงเหยื่อ `retrieval_strength` เป็นตัวตัดสินภายในชั้นเดียวกัน

**สิ่งที่นึกถึงบ่อยจึงไม่ใช่แค่หาง่ายขึ้น แต่หายยากขึ้นด้วย**

### 3.4 ขนาดคลังคือ "ขนาดสมอง"
```
store_budget_bytes    # ← "คนนี้ความจำดีแค่ไหน" กำหนดต่อ agent
```
ตั้งใหญ่ → อยู่ D0/D1 นาน จำรายละเอียดเยอะ · ตั้งเล็ก → ของที่ไม่ค่อยใช้ไหลลง D2/D3/D4 เร็ว
**ทุก policy ตอน benchmark ต้องอยู่ใต้ `store_budget` เดียวกัน**

## 4. สี่ภูมิภาค (P6)

> Squire: ระบบความจำของคนแยกกันจริง เสียหายแยกกันได้ (H.M. จำเหตุการณ์ใหม่ไม่ได้ แต่เรียนทักษะใหม่ได้)
> → การยัดทุกอย่างลง vector store ก้อนเดียวขัดกับหลักฐาน ไม่ใช่แค่ไม่เป็นระเบียบ

### 4.1 ตารางภูมิภาค

| ภูมิภาค | เก็บอะไร | index ด้วย | เข้า context | เจือจางถึง | OS analogue |
|---|---|---|---|---|---|
| `CORE` | ตัวตน · นิสัย · ค่านิยม | — (resident) | **ทุกครั้ง** | ❌ ห้าม | pinned kernel pages |
| `TRIGGER` | เมื่อไร/เมื่อเกิดอะไร → ทำอะไร | key ของเงื่อนไข | ไม่กิน context | ❌ ห้าม | interrupt vector table |
| `SKILL` | วิธีทำ · ลำดับการกระทำ | **cue ของสถานการณ์** | เมื่อสถานการณ์ตรง | D3 | demand-paged code |
| `ARCHIVE` | ประสบการณ์ · ความรู้ | similarity + เวลา | เมื่อเรียก | D4 | paged memory + page table |

**`CORE` และ `TRIGGER` ห้ามเจือจางเด็ดขาด** — นิสัยไม่เลือนเพราะความจำเต็ม ความตั้งใจไม่หายเพราะที่ไม่พอ
ทั้งสองมี **hard quota** ที่กันไว้ก่อน ที่เหลือค่อยเป็นของ `SKILL`/`ARCHIVE`

### 4.2 ★ `CORE` มี 3 ชั้น (McAdams) และชั้นบนสุดคือรากของ `ARCHIVE`

| ชั้น | คืออะไร | เปลี่ยนเร็วแค่ไหน |
|---|---|---|
| `CORE.trait` | ลักษณะกว้าง ๆ — "เป็นคนระวังตัว" | ช้ามาก (ปี) |
| `CORE.adaptation` | เป้าหมาย ค่านิยม วิธีรับมือ ผูกกับบทบาท | กลาง (เดือน) |
| `CORE.narrative` | เรื่องเล่าที่ร้อยทุกอย่างเป็นตัวตนที่ต่อเนื่อง | ช้า แต่เขียนใหม่ได้ |

> 🔗 **Conway บอกว่า life story schema เป็นตัว index ให้ lifetime periods · McAdams บอกว่า narrative identity
> คือชั้นบนสุดของบุคลิกภาพ — สองอันนี้คืออันเดียวกัน**
> → **`CORE.narrative` คือ root ของต้นไม้ `ARCHIVE`** ไม่ใช่สองคลังที่แยกขาด แต่เป็นยอดของต้นไม้เดียวกัน
> นี่คือกลไกจริงที่อธิบายว่าทำไม "ตัวตนมีผลต่อสิ่งที่นึกออก": **ตัวตนคือจุดตั้งต้นของการเดินทุกครั้ง**

### 4.3 ชั้นของ `ARCHIVE` (Conway + Tulving + fuzzy-trace)

```
L4  CORE.narrative        เรื่องเล่าตัวตน                        (root)
L3  lifetime period       "ตอนทำโปรเจกต์นี้"        เดือน–ปี
L2  general event    ★    "ช่วงที่แก้ dilution ladder"  วัน–สัปดาห์   ← จุดเข้าของการเดิน
L1  specific event        "ตอนที่ผลวัด binary ออกมา"    ชั่วโมง
L0  verbatim detail       ตัวเลข 0.214 ที่เห็นบนจอ      นาที         (ใบ)
```

**★ จุดเข้าอยู่ที่ L2 ไม่ใช่ root** — Conway พบว่า generative retrieval มัก**เริ่มที่ระดับ general event**
แล้วค่อยเจาะลงหรือถอยขึ้น (คนนึก *"ช่วงนั้นน่ะ ตอนที่..."* ออกก่อน รายละเอียดตามมาทีหลัง)
→ ประหยัดกว่าเริ่มจาก root ด้วย เพราะไม่ต้องเดินผ่านชั้นที่แยกแยะอะไรไม่ได้

### 4.4 `SKILL` ถูกเรียกด้วยสถานการณ์ ไม่ใช่ถูกค้นหา
งานฝั่ง habit นิยามนิสัยเป็นความเชื่อมโยง **context→response** ที่ทำงานโดยไม่ผ่านการคิดถึงเป้าหมาย
→ `SKILL` **ห้าม index ด้วย semantic similarity** เพราะ similarity ตอบ *"เรื่องนี้เกี่ยวกับอะไร"*
ไม่ใช่ *"ตอนนี้ควรทำอะไร"* · และตาม action-chunking หนึ่ง `SKILL` node = ลำดับการกระทำทั้งชุด

**และการนึกทักษะต้องไม่เดินผ่านต้นไม้ ARCHIVE เลย** — หลักฐานคือผู้ป่วย H.M. ที่สร้างความทรงจำใหม่
ไม่ได้เลยแต่ยังฝึกทักษะเก่งขึ้นทุกวัน ถ้าให้การนึกทักษะผ่านการค้นความทรงจำ = จำลองโครงสร้างที่หลักฐาน
ปฏิเสธไปแล้ว → เป็น **keyed lookup ที่ CUE, 0 ops**
(ตอนไม่มีข้อนี้ วัดได้ว่า `S` ตอบคำถามนิสัยได้ **0.000** ขณะที่ baseline ทุกตัวได้ 1.000)

### 4.5b นิสัยคือแบบแผน *ภายใน* ประสบการณ์
เกณฑ์เดิมบังคับให้ **ลูกทุกตัว**ของ node ต้องมี key ร่วม → กิจวัตรจะนับก็ต่อเมื่อไม่เคยมีเรื่องอื่นเกิด
ใต้หัวข้อเดียวกันเลย ซึ่งไม่เคยเป็นจริง → หา**กลุ่มย่อยที่เกาะกัน**แทน:
สิ่งเดียวที่ผ่านมาหลายครั้ง (content addressing ยุบเป็น node เดียวที่ occurrence สูง) หรือกลุ่มพี่น้องที่แทบเหมือนกัน

### 4.5 การตกผลึกนิสัย (`ARCHIVE` → `SKILL`/`CORE`)
```
เหตุการณ์ซ้ำ ๆ  --n_merged ≥ N และลูกกระจายตัวต่ำ-->  นิสัย
```
- "ลูกกระจายตัวต่ำ" = cos ระหว่างลูกสูง = **ทำแบบนี้ทุกครั้งจริง ไม่ใช่บังเอิญซ้ำ**
- deterministic ล้วน ไม่ต้องใช้ LLM · มีทางกลับ: นิสัยที่ถูกขัดบ่อยถูกลดชั้นลง `ARCHIVE`

### 4.6 งบสามก้อน (คนละสกุลเงิน)
```
context_budget_tokens   # RAM  — token ต่อการส่งเข้าโมเดลหนึ่งครั้ง
store_budget_bytes      # Disk — ขนาดคลัง = "ขนาดสมอง"
recall_ops_budget       # เวลา — จำนวนก้าวที่เดินได้ต่อการนึกหนึ่งครั้ง
```
**`recall_ops_budget` คือสิ่งที่ทำให้ต้นไม้มีค่าในกระดานคะแนน** — ถ้าการสแกนทั้งคลังยังฟรีเหมือนรอบเก่า
ต่อให้เขียนต้นไม้ที่สมบูรณ์แบบ ตัวเลขก็ไม่ขยับ

## 5. State machines

> ทำไมต้องเป็น FSM ไม่ใช่ฟังก์ชันเดียว: (1) **เร็ว** — แต่ละสถานะทำงานคนละแบบและ optimize แยกได้
> (2) **มีเพดาน** — นับก้าวได้ ตัดได้ ไม่มีทางวนไม่จบ (3) **อธิบายได้** — เส้นทางที่เดินคือคำอธิบาย
> (4) **agent เลือกได้อย่างปลอดภัย** — transition มีจำกัดและตรวจสอบได้ ต่างจากการปล่อยให้เรียกอะไรก็ได้

### 5.1 FSM ของการนึก — `RecallMachine`

```
        ┌──────┐
        │ IDLE │  ไม่มีการนึกค้างอยู่
        └───┬──┘
   perceive / query
            ▼
        ┌──────┐  สร้าง cue vector จากสิ่งเร้า + เลือกจุดเข้า
        │ CUE  │  ★ จุดเข้าคือชั้น general event (L2) ไม่ใช่ root (§4.3)
        └───┬──┘
            ├─── ตรงกับ CORE / TRIGGER ────────────┐  O(1) ไม่ต้องเดิน
            ▼                                      │
    ┌────────────────┐   descend / ascend / lateral│
    │    NAVIGATE    │◄──────────┐                 │
    │  beam ที่ละชั้น │           │                 │
    └───────┬────────┘ ──ก้าวต่อ──┘                 │
            │  ops หมด หรือ agent สั่ง stop         ▼
            ▼                              ┌──────────────┐
      ┌─────────────┐                      │  RESIDENT    │
      │ MATERIALIZE │◄─────────────────────┘              │
      └──────┬──────┘  แปลง node → payload ★ จ่าย token ที่นี่ที่เดียว
             ▼
      ┌─────────────┐  promote node ที่ใช้ (splay) · อัปเดตสถิติ · ปิด WalkPath
      │   SETTLE    │
      └──────┬──────┘
             ▼  IDLE
```

**เหตุผลของแต่ละสถานะ:**

| สถานะ | มีไว้ทำอะไร | ทำไมต้องแยกเป็นสถานะของตัวเอง |
|---|---|---|
| `IDLE` | ไม่มีการนึกค้าง | เป็นจุดที่ปลอดภัยสำหรับ snapshot/replay |
| `CUE` | แปลงสิ่งเร้าเป็นเวกเตอร์ + เลือกจุดเข้า | ที่เดียวที่โลกภายนอกเข้ามาได้ → ตรวจ input ที่เดียว |
| `RESIDENT` | ตอบจากของที่อยู่แล้ว | **ทางลัด O(1)** ที่ต้องไม่ปนกับการเดิน ไม่งั้นวัดต้นทุนแยกไม่ออก |
| `NAVIGATE` | เดินต้นไม้ | ที่เดียวที่ `recall_ops` ถูกใช้ → บังคับเพดานได้จุดเดียว |
| `MATERIALIZE` | แปลง node → ข้อความเข้า context | **ที่เดียวที่จ่าย token และที่เดียวที่แตะ `text_ref`** (V2) |
| `SETTLE` | promote + บันทึกเส้นทาง | ผลข้างเคียงทั้งหมดอยู่ที่เดียว → replay ง่าย, ไม่มี state เปลี่ยนกลางการเดิน |

**transition ที่ agent เลือกได้ (เปิดเป็น tool):**

| tool | ความหมาย | ต้นทุน | ที่มา |
|---|---|---|---|
| `descend(k)` | เจาะลงหาที่ละเอียดขึ้น | 1 op + อ่าน k centroid | Conway: เดินลงจาก general event |
| `ascend()` | ถอยขึ้นหาแก่นที่กว้างขึ้น | 1 op | Conway: เดินขึ้นเมื่อเจาะผิดกิ่ง |
| `lateral(k)` | เดินข้างไปเรื่องที่เชื่อมโยงกัน | 1 op + อ่าน k | spreading activation |
| `materialize(addr)` | ดึงเข้า context จริง | token ตามขนาด | — |
| `stop()` | พอแล้ว | 0 | — |

- **engine เป็นคนเดินและตรวจ agent เป็นคนเลือกทิศ** — เกิน `recall_ops_budget` ระบบตัดเอง
- **fast path ต้องเป็นนักค้นหาจริง ไม่ใช่ของหลอก** — ใช้ **best-first ที่มี frontier เดียวทั้งการเดิน**
  ไม่ใช่ greedy ทีละชั้น เพราะ greedy **ถอยกลับจากทางที่เลี้ยวผิดไม่ได้**: วัดจริงแล้วมันหยิบ
  "เพื่อนบ้าน" ของสิ่งที่ต้องการกลับมา 4 ชิ้น ขณะที่ของจริงนอนอยู่ลึก 5 ชั้นแบบไม่จางเลย และ ops เหลือเพียบ
  → คนก็ไม่ได้ค้นแบบนั้น *"ไม่ใช่ทริปนั้น อีกทริปนึง"* คือการถอยกลับ ซึ่งเป็นเหตุผลที่มี `ASCEND`/`LATERAL` ตั้งแต่แรก
  **ผลหลังแก้: detail 0.80 → 1.00 ที่ budget ใหญ่ และ 0.32 → 0.52 ที่ budget เล็ก**
- **ทุกก้าวถูกบันทึกใน `WalkPath` → `explain()` ได้ฟรี**

### 5.2 FSM ของ `TRIGGER`

```
                 ┌─────────────────────────────────┐
                 ▼                                 │
   (intend) → ARMED ──เงื่อนไขตรง──► FIRED ──ทำสำเร็จ──┤
                 │                     │            │ (ถ้าเป็น trigger ซ้ำได้)
                 │                     └──ทำไม่ได้──► SUSPENDED
                 │                                        │
                 └──────────ยกเลิก / หมดอายุ──────► RETIRED ◄┘ (ทำสำเร็จ ครั้งเดียวจบ)
```

**`SUSPENDED` ไม่ใช่สถานะที่คิดเอง** — งานวิจัย prospective memory พบว่า intention ที่ค้างอยู่
**ยังผุดขึ้นเองได้** ส่วนที่จบแล้วไม่ผุด → `SUSPENDED` ต้องยังถูกตรวจ ส่วน `RETIRED` ไม่ต้อง

**สามชนิด ต้นทุนไม่เท่ากัน — และความไม่เท่านี้มีที่มา:**

| ชนิด | เก็บยังไง | ต้นทุน | ที่มา |
|---|---|---|---|
| `TRIGGER.event` "ถ้าเจอ X ให้ทำ Y" | hash bucket ตาม event key | **O(1) ฟรี** | spontaneous retrieval |
| `TRIGGER.time` "ทุกเช้า 8 โมง" | timer wheel เรียงตาม tick | **O(1) ต่อ tick** | — |
| `TRIGGER.predicate` "ถ้า mood < k" | เดินตรวจ predicate ที่ compile แล้ว | **จ่าย `recall_ops` จริง** | monitoring — แพงจริงในคนด้วย |

> ต้นทุนใน cost model จึงสะท้อนต้นทุนทางปัญญาจริง ไม่ใช่ตัวเลขที่ตั้งขึ้นลอย ๆ

### 5.3 FSM วงจรชีวิตของ node

```
    NEW ──► HOT ⇄ WARM ⇄ COLD ──►ความจุเต็ม──► DILUTED(D1→D2→D3→D4) ──► MERGED(อยู่ในแม่)
             ▲                                        │                        │
             └──────────── ถูกเรียกใช้อีก ─────────────┴────────────────────────┘
                     (ตื้นขึ้น — แต่ fidelity ไม่กลับมา)
```

- `HOT/WARM/COLD` = **ตำแหน่งบนแกนความลึก** (retrieval strength)
- `DILUTED/MERGED` = **ตำแหน่งบนแกนความคมชัด** (storage strength)
- **การเจือจางเป็นทางเดียว** — นึกถึงอีกครั้งทำให้ *เข้าถึงง่ายขึ้น* แต่ *รายละเอียดที่หายไปแล้วไม่กลับมา*
  ตรงกับ Bjork (retrieval practice ยกเฉพาะ retrieval strength) และกับ §5.6 ของ north star
  ที่ห้าม reconstructive recall แบบแต่งเติมของเดิม

### 5.4 FSM ของ consolidation ("การนอน")

```
AWAKE ──ทุก N tick หรือคลังใกล้เต็ม──► REPLAY ──► ABSTRACT ──► REBALANCE ──► ENFORCE ──► AWAKE
```

| สถานะ | ทำอะไร |
|---|---|
| `REPLAY` | อ่าน event ในหน้าต่างเวลาแบบสลับ (interleaved) |
| `ABSTRACT` | ยุบเหตุการณ์ซ้ำเป็นความรู้ · ตกผลึกนิสัยขึ้น `CORE`/`SKILL` (§4.5) |
| `REBALANCE` | sink ของที่ไม่ถูกใช้ · แตก/ยุบ node ให้ branching เหมาะสม |
| `ENFORCE` | บังคับ `store_budget` ด้วยบันได D (§3.2) |

**ทำไมต้อง batch ไม่ใช่ทำทันทีทุก observation:** Complementary Learning Systems (McClelland et al. 1995)
อธิบายว่าถ้าระบบที่สกัดโครงสร้างเรียนเร็วเกินไปจะเกิด **catastrophic interference** ของใหม่ทับของเก่าพัง
สมองแก้ด้วย replay แบบสลับตอนหลับ → **เหตุผลเชิงกลไก ไม่ใช่แค่ "ประหยัดค่า LLM"**

## 6. การวัด — ทิศทางใหม่

> เมื่อ agent เลือกเองได้ การวัดแบบ "policy ตัดสินใจถูกกว่า" ใช้ไม่ได้
> **ทางออก: วัด "รูปร่างความสามารถ" ของโครงสร้าง ซึ่งเป็นสมบัติของโครงสร้าง ไม่ใช่ของการเลือกของ LLM**

### M1 — เส้นโค้งความจุ ★ ตัวชี้ขาดใหม่
```
x = store_budget_bytes    y = สองเส้นแยกกัน: detail และ gist
```
- ✅ ถูก: detail ลาดลง แต่ **gist แบนเกือบตลอด** = "ลืมรายละเอียด แต่พอจำได้"
- ❌ ผิด: สองเส้นตกพร้อมกันเป็นหน้าผา

**นี่คือ fuzzy-trace theory ที่พล็อตเป็นกราฟได้** และแทบไม่มีใครในวงการพล็อต เพราะระบบอื่น
ไม่มีแนวคิด "คลังมีขนาด"

| | |
|---|---|
| **M2** | quality เทียบ `context_budget` ที่คลังเท่ากัน — ข้ออ้าง "context ไม่บวม" |
| **M3** | `recall_ops` และ ms เทียบขนาดคลัง — ต้อง ~log ไม่ใช่เชิงเส้น · **deterministic 100% แม้ LLM อยู่ในลูป** |
| **M4** | อัตราขัดแย้งกับ `CORE` ตลอด session ยาว — สมบัติของโครงสร้าง |
| **M5** | trigger ยิงตรงเวลา / พลาด / ยิงมั่ว — **ไม่แตะ LLM เลย** |
| **M6** | % คำตอบที่มี `WalkPath` ครบ + `memory_causality` |
| **M7** | replay ตรงเป๊ะด้วย VCR |
| **M8** | LoCoMo / LongMemEval เทียบ MemGPT/Letta, Mem0, Zep |

### OPT oracle ยังใช้ได้ — เปลี่ยนเป้า
เดิม "ถ้ารู้อนาคต ควรใส่อะไรใน context" → ใหม่ **"ถ้ารู้อนาคต ควรจัดสรรคลังขนาด M ยังไง"**
ยังคำนวณ offline ได้ ยังได้ `competitive_ratio` และ **โค้ด oracle เดิมใช้ต่อได้**
